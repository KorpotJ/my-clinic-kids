# My Clinic Kids

ระบบจองคิวและติดตามพัฒนาการสำหรับคลินิกกิจกรรมบำบัดเด็ก
ผู้ปกครองใช้งานผ่าน LINE · เจ้าหน้าที่ใช้แผงควบคุมบนเว็บที่ยืนยันตัวตนด้วย Cognito และบังคับ MFA

สถาปัตยกรรมแบบ serverless บน AWS ภูมิภาค **ap-southeast-7 (กรุงเทพฯ)** เพื่อให้ข้อมูลส่วนบุคคลอยู่ในประเทศ

## ภาพรวม

| | |
|---|---|
| **โค้ดที่เขียนเอง** | ~8,860 บรรทัด — Lambda 3,060 · LINE LIFF 2,454 · แผงเจ้าหน้าที่ 3,276 |
| **ประมวลผล** | Lambda 13 ฟังก์ชัน (Node.js) |
| **API** | 26 เส้นทางบน API Gateway HTTP API · authorizer 2 ชนิด · ไม่มีเส้นทางที่เปิดโล่ง |
| **ฐานข้อมูล** | PostgreSQL 18.3 — 8 ตาราง · 53 constraints · 13 indexes |
| **Migration** | ไฟล์ SQL 4 ตัว · สองตัวที่แก้ constraint เดิมมีสคริปต์ rollback คู่กัน |
| **ตัวตน** | LINE (ผู้ปกครอง) · Amazon Cognito บังคับ MFA (เจ้าหน้าที่) |
| **สิทธิ์การเข้าถึง** | 4 บทบาทใน `cognito:groups` · ปฏิเสธเป็นค่าตั้งต้น |
| **ค่าใช้จ่ายจริง** | ~$34/เดือนก่อนปลดระวาง · 95% มาจาก RDS กับ VPC endpoint ตัวเดียว |

สถานะ: ทำครบตามขอบเขตที่ตั้งไว้ ใช้งานได้จริงพร้อมข้อมูลเดโม 8 เคส ไม่เคยมีข้อมูลผู้ป่วยจริงในระบบ ปัจจุบันปลดระวางชั้นฐานข้อมูลแล้ว เก็บไว้เป็น RDS snapshot

## ทำไมถึงสร้าง และทำไมถึงหยุด

เริ่มจากการอยากทำแลบ AWS ผมต้องการโปรเจกต์ที่ใหญ่พอจะบังคับให้ต้องตัดสินใจเรื่อง VPC ตัวตน และค่าใช้จ่ายจริงๆ ไม่ใช่ stack ตามบทเรียนที่ไม่เคยต้องเจอของจริง

โจทย์มาจากแฟนผมซึ่งเป็นนักกิจกรรมบำบัดที่ฝึกงานอยู่ในคลินิกเด็กที่เพิ่งเปิดใหม่ การมีตัวกลางสำหรับจองคอร์สระหว่างผู้ปกครองกับคลินิกดูเข้าท่า — ผู้ปกครองทักถามคิวทาง LINE เจ้าหน้าที่เปิดสมุดดู

พอระบบใช้งานได้จริงแล้ว ผมติดต่อไปเสนอกับคลินิก **คำตอบของเขาคือสิ่งที่มีค่าที่สุดที่โปรเจกต์นี้ให้มา** — คอร์สของเขาล็อกตามวันในสัปดาห์อยู่แล้ว เด็กแต่ละคนฝึกโปรแกรมเดิมซ้ำ ผู้ปกครองจึงไม่มีอะไรให้เลือก ตัวกลางสำหรับจองแก้ปัญหาที่เขาไม่มี

ค่ารันระบบราว 1,100 บาทต่อเดือน เมื่อไม่มีปัญหาที่คุ้มกับค่านี้ ผมจึงหยุดและปลดระวางส่วนที่มีค่าใช้จ่ายออก

ผมยังคิดว่าระบบนี้น่าพัฒนาต่อ — ส่วนตารางฝึก บันทึกพัฒนาการ และแผงเจ้าหน้าที่ยืนอยู่ได้ด้วยตัวเอง สิ่งที่พลาดคือเฉพาะขั้นตอนการจอง แต่การทำต่อโดยไม่มีคนขอ ก็คือความผิดพลาดเดิมในรูปแบบที่ยาวขึ้น

### วิธีที่ใช้สร้าง

ผมใช้ AI เป็นตัวขับเคลื่อนการเขียนโค้ดเป็นหลัก และทำหน้าที่เป็นผู้กำกับงานเป็นส่วนใหญ่ — วางสถาปัตยกรรม แบ่งงานเป็นชิ้น ตรวจผลแต่ละชิ้นกับระบบจริง และทิ้งสิ่งที่ตรวจแล้วไม่ผ่าน ผมไม่ได้อ้างว่าเข้าใจโค้ดทุกบรรทัด

สิ่งที่ผมอ้างได้คือวินัยในการตรวจสอบรอบๆ มัน **ตัวเลขทุกตัวใน README นี้วัดจากระบบจริง** — จำนวนบรรทัด จำนวน route นิยาม constraint ค่าใช้จ่าย กลุ่มสิทธิ์ — ไม่ได้จำมาหรือประมาณเอา และหัวข้อ "ปัญหาที่รู้อยู่" ก็เป็นผลผลิตจากกระบวนการเดียวกัน ทุกข้อพบจากการเอาระบบจริงไปเทียบกับสิ่งที่เอกสารอ้าง และหลายข้อขัดกับสิ่งที่ผมเคยเชื่อว่าจริง

```

      │                                     │
      │ LIFF                                │ Cognito Hosted UI
      │                                     │ OAuth2 authorization code + MFA
      ▼                                     ▼
  CloudFront ─────────────────────► S3 (private ปิดสาธารณะทุกชั้น)
      │
      ▼
  API Gateway — HTTP API 26 เส้นทาง
      ├──  8 เส้น → LINE token authorizer (REQUEST · Lambda เขียนเอง)
      └── 18 เส้น → Cognito JWT authorizer + ตรวจ role ในโค้ด
      │
      ▼
  Lambda × 13
      ├── 10 ตัวใน VPC ──┬──► RDS PostgreSQL (subnet ส่วนตัว · เข้ารหัส)
      │                  └──► VPC Interface Endpoint ──► Secrets Manager
      └──  3 ตัวนอก VPC ──┬──► LINE Messaging API
                          └──► Cognito Admin API

  ไม่มี NAT Gateway ในบัญชีเลย
```

### การตัดสินใจที่ต้องอธิบายได้

**ไม่ใช้ NAT Gateway** — NAT Gateway ราคาราว $32/เดือน แพงกว่าทั้งระบบรวมกัน จึงวาง Lambda 10 ตัวที่แตะฐานข้อมูลไว้ใน VPC ที่ไม่มีทางออกอินเทอร์เน็ต แล้วให้เข้าถึง Secrets Manager ผ่าน PrivateLink interface endpoint ส่วน 3 ตัวที่จำเป็นต้องยิงออกเน็ตจริง (LINE Messaging, Cognito Admin) วางไว้นอก VPC ทั้งหมด

**ไม่มีความลับในโค้ดหรือ environment variable** — ทุกฟังก์ชันดึงข้อมูลรับรองจาก Secrets Manager ตอนรัน ไม่มีรหัสผ่านฐานข้อมูลใน `process.env` และไม่มีใน repository

**audit ของฝั่งจัดการเจ้าหน้าที่ใช้ CloudTrail ไม่ใช่ตารางในฐานข้อมูล** — ฟังก์ชันที่จัดการบัญชีเจ้าหน้าที่อยู่นอก VPC จึงเขียน RDS ไม่ได้ แทนที่จะเพิ่ม NAT Gateway เพื่อให้ audit ทางเดียวทำงานได้ จึงอาศัยข้อเท็จจริงที่ว่า Cognito Admin API ถูกบันทึกใน CloudTrail อยู่แล้ว ยืนยันด้วยการตรวจว่า `AdminListGroupsForUser` ปรากฏใน event history จริง

**การกันจองซ้ำอยู่ที่ฐานข้อมูล ไม่ใช่ที่หน้าจอ** — ปุ่มจองปิดตัวเองฝั่ง client แต่หลักประกันจริงคือ partial unique index

```sql
CREATE UNIQUE INDEX uniq_child_per_session
  ON bookings (child_id, session_id)
  WHERE status IS DISTINCT FROM 'cancelled';
```

เมื่อเกิด `23505` จะถูกแปลงเป็น `409 ALREADY_BOOKED` การเช็คด้วย `SELECT` ก่อน `INSERT` มีช่องว่างให้เกิด race condition เสมอ แต่ constraint ไม่มี

**การกันนักบำบัดคาบชนใช้ exclusion constraint** เพื่อปฏิเสธช่วงเวลาที่ทับซ้อนกัน ไม่ใช่แค่เวลาเริ่มตรงกัน

```sql
EXCLUDE USING gist (
  therapist_id WITH =,
  tstzrange(starts_at, ends_at) WITH &&
) WHERE (status <> 'cancelled')
```

**บันทึกทางคลินิกถูกแยกตั้งแต่ระดับ schema** — ตาราง `session_notes` มีสองคอลัมน์: `clinical_note` ที่ไม่เคยออกจากแผงเจ้าหน้าที่ และ `parent_summary` ที่แอปผู้ปกครองแสดง เจ้าหน้าที่กรอกทั้งสองช่องในฟอร์มเดียว แต่แอปผู้ปกครองไม่มีเส้นทาง API ที่คืนค่าช่องคลินิกได้เลย

**ไม่มีการลบถาวรในการใช้งานปกติ** — ข้อมูลเด็ก คอร์ส บัญชีเจ้าหน้าที่ และคาบที่ยกเลิก ทั้งหมดย้ายเข้าแฟ้มจัดเก็บและกู้คืนได้ ปุ่มลบถาวรมีเฉพาะในหน้าแฟ้มจัดเก็บเท่านั้น

## ความปลอดภัย

- RDS ไม่มี public endpoint · security group อนุญาตพอร์ต 5432 **จาก security group ต้นทางเพียงตัวเดียว** ไม่มี CIDR ใดถูกอนุญาต แม้แต่ของ VPC ตัวเอง
- เปิดการเข้ารหัสข้อมูลที่จัดเก็บ · automated backup 7 วัน · ถ่าย manual snapshot ก่อนทุก migration
- S3 ต้นทางเปิด public access block ครบทั้ง 4 ชั้น และไม่มี bucket policy เข้าถึงได้ผ่าน CloudFront เท่านั้น
- Cognito บังคับ MFA ทุกบัญชี · รหัสผ่านขั้นต่ำ 8 ตัวครบทั้ง 4 ประเภทอักขระ · รหัสชั่วคราวหมดอายุใน 7 วัน · การกู้บัญชีมี 2 ขั้น
- ระบบไม่เคยจัดการรหัสผ่านเจ้าหน้าที่เอง — ใช้ OAuth2 authorization code flow ผ่าน Cognito Hosted UI
- การตรวจ role เป็นแบบปฏิเสธก่อน: token ที่ไม่มีกลุ่มที่รู้จักได้ `403` ไม่ใช่สิทธิ์เริ่มต้น

บันทึกปัญหาที่พบและแก้ระหว่างการตรวจครั้งสุดท้ายอยู่ใน `docs/security-findings.md`

## ระบบทำอะไรได้

### ฝั่งผู้ปกครอง — LINE LIFF

- **LINE official account พร้อม rich menu** — เปิดแอปในไลน์ ไม่ต้องติดตั้งอะไร ไม่ต้องมีรหัสผ่านแยก
- **คอร์สเดี่ยวจองเองได้ทันที** — เลือกคอร์ส เลือกเวลา จบ
- **คอร์สกลุ่มส่งต่อเข้าแชท** — การจัดองค์ประกอบกลุ่มขึ้นกับช่วงวัยและระดับทักษะ ซึ่งเป็นดุลยพินิจของนักบำบัด ปุ่มจึงเป็น "ดูรอบที่เปิดรับสมัคร" ไม่ใช่ปุ่มจอง
- **บันทึกพัฒนาการหลังเข้าฝึกทุกครั้ง** เขียนโดยนักกิจกรรมบำบัด ผู้ปกครองเห็นเฉพาะส่วนสรุปสำหรับผู้ปกครอง
- **แจ้งเตือนนัดหมาย** ส่งเป็น push message ทาง LINE

### ฝั่งเจ้าหน้าที่ — แผงควบคุมบนเว็บ

- **ตารางแบบ ปี / เดือน / วัน** พร้อมตัวนับคาบเรียน การจอง และคำขอที่รออนุมัติ
- **คำขอจองต้องผ่านการอนุมัติ** ก่อนกลายเป็นคาบที่ยืนยันแล้ว
- **ฟอร์มบันทึกแยกช่องคลินิกกับช่องผู้ปกครอง** มีป้ายกำกับในหน้าจอให้เห็นความต่างขณะพิมพ์
- **จัดการบัญชีและบทบาทเจ้าหน้าที่** ผ่าน Cognito Admin API ไม่มีตารางผู้ใช้ในฐานข้อมูล

## ปัญหาที่รู้อยู่

รายการตามจริงทั้งหมด ตรวจสอบด้วยการวัด ไม่ใช่การเดา

| ปัญหา | ผลกระทบ |
|---|---|
| Cognito มี 4 กลุ่ม แต่โค้ดรู้จักแค่ `ClinicDirector` กับ `Admin` | บัญชีที่เป็น `OT` หรือ `SpecialEd` ล็อกอินได้แต่ถูกปฏิเสธทุกเส้นทาง ทั้งที่ dropdown ในหน้าจอมีให้เลือกครบทั้งสี่ |
| ฟอร์มบันทึกพัฒนาการไม่ดึงค่าเดิมมาแสดง | กด "ดู/แก้" แล้วได้ฟอร์มเปล่าแม้จะมีบันทึกอยู่ ข้อมูลที่บันทึกไว้ยังอยู่ครบและแสดงในแอปผู้ปกครองปกติ |
| migration ที่จะเพิ่ม `UNIQUE (booking_id)` ให้ `session_notes` ไม่เคยถูกรัน | ไม่มีอะไรกันไม่ให้หนึ่ง booking มีหลายบันทึก |
| exclusion constraint คืน SQLSTATE `23P01` ไม่ใช่ `23505` | โค้ดที่ดักเฉพาะ `23505` จะคืน `500` แทน `409` ในเส้นทางสร้างคาบฝั่งแอดมิน ยังไม่ได้ตรวจในโค้ด |
| `notification_log` ไม่เคยถูกเขียนเลย | ตัวส่งการแจ้งเตือนไม่มีไดรเวอร์ฐานข้อมูล ตารางมีอยู่แต่ว่างเปล่า |
| ชื่อทรัพยากรไม่ตรงกันเพราะเปลี่ยนชื่อโปรเจกต์กลางทาง | instance ชื่อ `mck-db` · secret ชื่อ `babyplaytime/db-credentials` · ฐานข้อมูลชื่อ `babyplaytime` การเปลี่ยนชื่อต้อง deploy ใหม่ 12 ฟังก์ชัน จึงเลือกเขียนเอกสารกำกับแทน |
| หน้าแดชบอร์ดเป็น placeholder | วางขอบเขตไว้แล้วแต่ยังไม่ได้ทำ |
| log เก็บ 14 วัน และไม่ได้สร้าง CloudTrail trail | event history ครอบคลุม 90 วัน เพียงพอสำหรับเดโม แต่ไม่พอสำหรับการใช้งานจริง |

## สถานะโปรเจกต์

หยุดหลังทำครบตามขอบเขตที่ตั้งไว้ ด้วยเหตุผลที่อธิบายไว้ข้างต้น

เพื่อไม่ให้มีค่าใช้จ่ายค้าง ได้ลบ RDS instance และ VPC endpoint ของ Secrets Manager ออก โดยเก็บฐานข้อมูลไว้เป็น manual snapshot 5 ตัว รวมถึงตัวที่ถ่ายทันทีก่อนลบ ส่วนที่เหลือ — Lambda, API Gateway, Cognito, CloudFront, S3 — แทบไม่มีค่าใช้จ่ายจึงยังคงอยู่ หน้าจอทั้งหมดยังเปิดดูได้แม้ข้อมูลจะไม่โหลดแล้ว
